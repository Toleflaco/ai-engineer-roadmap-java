## Bloque S15-part-4: pipeline CI/CD

### Conceptos previos al YAML (media hora conceptual)

Antes de escribir workflow, mapa mental para llevarse a entrevistas.

**Distinción CI vs CD vs plataforma de destino**. Corrección de la confusión común "Kubernetes es CD":

- **CI (Continuous Integration)**: automatiza el **build** y la verificación. Cada push → servidor compila, testea, construye imagen. Resultado: artefacto validado. **Lo que se monta hoy**.
- **CD (Continuous Delivery/Deployment)**: automatiza el **deploy**. Toma el artefacto de CI, lo empuja a un registry, y le dice a la plataforma de destino que lo use. **Nunca ejecuta**.
- **Plataforma de destino** (Kubernetes / ECS / VM con systemd / Heroku / Lambda): **ejecuta y gestiona** los procesos. Es el destino de CD.

Regla mental locked: **CI = build. CD = deploy. La plataforma de destino = run.** Tres verbos distintos, tres responsabilidades distintas.

**Analogía Amazon** para fijarlo: CI es la fábrica que produce la caja. CD es el mensajero que la lleva. Kubernetes (o ECS, o VM) es el almacén de destino. El mensajero no es el almacén.

**Qué es un registry**: almacén online de imágenes Docker con protocolo estándar `push`/`pull`. Docker Hub, GHCR, AWS ECR, GCR, ACR. Símil directo: Maven Central para JARs, npm registry para librerías JS. Solo dos operaciones básicas, nada más.

**Qué es un Deployment de Kubernetes** (matiz importante para no confundirlo con CD): objeto declarativo que declara **cómo debe correr la app**: qué imagen, cuántas réplicas, qué recursos, qué probes, qué estrategia de update. `kubectl apply` no ejecuta directamente; Kubernetes reconcilia el estado real con el declarado.

**Flujo completo real** (referencia futura para post-Bash roadmap):

```
push a main → CI (mvn verify + docker build + smoke test) → OK
             → CD (docker push a registry + kubectl apply) → OK
             → Kubernetes reconcilia Deployment: pullea, arranca pods nuevos,
                espera readinessProbe, mata pods viejos, tráfico enrutado
```

### Anatomía de un workflow de GitHub Actions

```
workflow (.github/workflows/*.yml)
├── name (opcional, aparece en UI)
├── on: (eventos que disparan)
└── jobs:
    └── <job-name>:
        ├── runs-on: (runner)
        ├── needs: (dependencias entre jobs, opcional)
        └── steps:
            ├── uses: <owner>/<repo>@<version>
            └── run: <shell command>
```

**Regla mental lockeada**: cada job corre en un **runner fresco** (VM efímera). Los jobs NO comparten disco entre sí. Las steps dentro del mismo job SÍ comparten disco. Para pasar artefactos entre jobs: `actions/upload-artifact` + `actions/download-artifact`.

**Trigger `pull_request` — matiz crítico**: cuando abres PR contra `main` desde `feature/x`, GitHub Actions **NO ejecuta el CI sobre `main` ni sobre `feature/x`**. Ejecuta sobre la **fusión hipotética** — un merge commit virtual que GitHub calcula al vuelo. Por eso detecta conflictos semánticos (código que Git no marca como conflicto pero que rompe el build post-merge). Sin esto, verías el fallo después del merge, con main roto para todos.

**Version pinning**: siempre `@vN` mayor (`actions/checkout@v5`), nunca `@main` ni `@latest` (que ni existe en Actions). Equilibrio entre reproducibilidad y recibir patches automáticos.

### YAML de sintaxis conceptual

Dos block scalars de YAML:

- **`|` (literal block)**: preserva saltos de línea. Para scripts bash, HTML, cualquier cosa donde `\n` importa.
- **`>` (folded block)**: convierte saltos en espacios. Para prosa multi-línea que debe parsear como una sola línea.

Regla mental lockeada: `|` para scripts, `>` para prosa.

Dos estilos de listas:

- **Flow style**: `branches: [main]` (compacta, una línea).
- **Block style**: `branches:\n  - main` (multi-línea, con guiones).

Ambas semánticamente equivalentes. **Convención de la comunidad Actions y templates oficiales**: block style, por consistencia con el ecosistema. Adoptada.

### Bug de indentación en Job 2 (empírico)

Primer intento del YAML de Job 2:

```yaml
- name: Checkout code
- uses: actions/checkout@v4
```

Cada guion `-` en YAML abre un elemento de lista nuevo. Interpretación resultante: dos steps, una con solo `name` (sin acción, error) y otra sin nombre.

Regla mental lockeada: **cada step es UN único elemento de lista con múltiples propiedades. `name:`, `uses:`, `run:`, `with:` van todas al mismo nivel de indentación, SIN guion propio**. Sub-mappings como `with:` van indentados más adentro.

Corregido a la forma correcta. Analogía útil: en JSON sería un objeto con múltiples campos; el guion abre el objeto, todo lo demás va dentro.

### YAML final del workflow inicial

```yaml
name: CI - erp-mcp-server

on:
  push:
    branches:
      - main
  pull_request:
    branches:
      - main

jobs:
  build-and-test:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Install Java 21
        uses: actions/setup-java@v4
        with:
          java-version: '21'
          distribution: 'temurin'
          cache: 'maven'

      - name: Run Maven verify
        run: mvn verify

  docker-build:
    runs-on: ubuntu-latest
    needs: build-and-test
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Build Docker image
        run: docker build -t erp-mcp-server:ci .

  smoke-test:
    runs-on: ubuntu-latest
    needs: docker-build
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Start compose stack
        run: docker compose up --build -d --wait --wait-timeout 60

      - name: Verify MCP endpoint responds
        run: |
          for i in {1..10}; do
            response=$(curl -s -o /dev/null -w "%{http_code}" http://localhost:8080/mcp)
            if [ "$response" = "400" ]; then
              echo "MCP endpoint responded with expected 400"
              curl -s http://localhost:8080/mcp | grep -q "Invalid Accept header" && exit 0
            fi
            echo "Attempt $i: got $response, retrying in 2s..."
            sleep 2
          done
          echo "MCP endpoint did not respond as expected after 10 attempts"
          exit 1

      - name: Show logs on failure
        if: failure()
        run: docker compose logs

      - name: Stop compose stack
        if: always()
        run: docker compose down
```

### Primer arranque del pipeline: FALLO diagnosticado a fondo

Al pushear, GitHub disparó el workflow automáticamente. Estado:

- **build-and-test**: verde en ~2min.
- **docker-build**: verde en ~4min.
- **smoke-test**: **rojo** con `Error: Process completed with exit code 56`.

Tres warnings adicionales:
- `Node.js 20 is deprecated. Actions actions/checkout@v4 and actions/setup-java@v4 forced to run on Node.js 24`.
- `setup-java v4 is deprecated. Please migrate to actions/setup-java@v5`.

**Diagnóstico paso a paso** (aplicando la técnica de leer logs de forma exhaustiva):

**Exit code 56 de curl**: "Failure in receiving network data". Conexión establecida pero respuesta no recibida completa. Típicamente connection refused o reset por peer.

**Ausencia de intentos en el log**: el bucle debería imprimir `Attempt X: got Y, retrying in 2s...` en cada iteración. **Ningún `Attempt X` en el log**. Eso significa que el script abortó **en la primera línea del primer curl**, antes de llegar al `echo` o `sleep`.

**Causa raíz — set -e en el runner**: `shell: /usr/bin/bash -e {0}` visible en el log. Con `set -e` activo, cualquier comando con exit no cero aborta el script **inmediatamente**. `curl` sale con 56, `set -e` mata el script, no hay retry posible.

**Causa raíz secundaria — `docker compose up --wait` insuficiente**: el servicio `app` en el compose **no tiene healthcheck definido**. `--wait` considera "healthy" a un contenedor `running` si no hay healthcheck declarado. Retorna en cuanto el contenedor de `app` está `running`, sin comprobar si Spring dentro ha abierto el 8080. En un runner de GitHub (menos CPU, disco compartido), Spring tarda ~5-10s tras `running` en servir peticiones.

**Confirmación empírica**: el step `Show logs on failure` mostró **cero líneas de `erp-app`**. Solo logs de `erp-postgres`. Spring no había tenido tiempo ni de imprimir el banner cuando `docker compose logs` corrió.

Regla mental lockeada CRÍTICA: **en bash con `set -e`, comandos dentro de `$(...)` que salen con exit no cero pueden matar el script antes de que la lógica del bucle evalúe el resultado**. Solución: `|| echo <fallback>` en las capturas de curl para que la sustitución de comandos nunca propague el fallo.

Regla mental lockeada CRÍTICA 2: **`docker compose up --wait` sin healthcheck del servicio target retorna en cuanto el contenedor está `running`, no cuando el servicio dentro está listo**. Para verificación real, healthcheck en compose o polling activo con retry robusto.

Meta-regla mental lockeada: **un smoke test tiene que TOLERAR fallos transitorios, no romperse al primero**. Es exactamente lo que un smoke test valida (que el sistema se estabiliza), así que el script debe reflejarlo.

### Fix aplicado

```yaml
- name: Verify MCP endpoint responds
  run: |
    for i in {1..15}; do
      response=$(curl -s -o /dev/null -w "%{http_code}" http://localhost:8080/mcp || echo "000")
      if [ "$response" = "400" ]; then
        body=$(curl -s http://localhost:8080/mcp || echo "")
        if echo "$body" | grep -q "Invalid Accept header"; then
          echo "MCP endpoint responded with expected 400 and message"
          exit 0
        fi
      fi
      echo "Attempt $i: got HTTP $response, retrying in 3s..."
      sleep 3
    done
    echo "MCP endpoint did not respond as expected after 15 attempts"
    exit 1
```

Cambios:

1. **`|| echo "000"` en los dos curls**. Si curl falla, la variable queda con valor conocido (`000` o cadena vacía) y el bucle continúa evaluando en vez de abortar.
2. **15 intentos × 3 segundos = 45s de gracia**. Suficiente para runners lentos incluso con warm-up de JVM.
3. **Verificación en dos pasos**: primero status code, después body. Cada uno protegido.
4. **Print del HTTP code en cada intento** para diagnóstico visible en logs.

Y en el mismo commit:

5. **`actions/checkout@v4` → `@v5`** (3 sitios). Cierra warning de Node.js 20.
6. **`actions/setup-java@v4` → `@v5`**. Cierra warning de deprecación.

Commit `309f561` con mensaje bilingüe `fix(ci): make smoke test resilient to transient curl failures and bump actions`. Prefijo `fix(ci):` porque arregla pipeline roto, no configuración nueva.

## Deudas operacionales lockeadas nuevas

### `set -e` + captura de comandos (`$(...)`) es doble filo en bash

En scripts CI (donde `set -e` suele estar activo por defecto), cualquier comando con exit no cero dentro de `$(...)` aborta el script antes de que la lógica pueda decidir qué hacer.

Regla: en bucles de retry que capturan output de comandos falibles, **siempre añadir `|| echo <fallback>` (o `|| true`) a la captura** para asegurar que la sustitución nunca propaga el exit al script.

Aplicable no solo a curl: cualquier `command_that_can_fail` dentro de `$(...)` bajo `set -e`.

### `docker compose up --wait` sin healthcheck del servicio target

`--wait` considera "healthy" a cualquier contenedor `running` si el servicio no tiene healthcheck declarado. No espera al servicio dentro del contenedor.

Regla: si `--wait` es la única sincronización antes de tests, **el servicio target debe tener healthcheck declarado**. Si no puede tenerlo (dependencia externa, arranque irregular), complementar con polling activo con retry en el script de test.

Nota operacional: cuando se añada el actuator y HEALTHCHECK del Dockerfile (deuda MEDIA), añadir también healthcheck al servicio `app` en `docker-compose.yml` para que `--wait` sea confiable sin necesidad de polling secundario.

### `sleep` fijo en CI es anti-patrón

Motivo 1: puede quedarse corto (runners de Actions son menos rápidos que dev local, timing variable).
Motivo 2: casi siempre desperdicia tiempo cuando el servicio arranca rápido.

Alternativas correctas:
- `docker compose up --wait --wait-timeout N` si hay healthchecks confiables.
- Bucle de polling con retry contra el propio endpoint objetivo.
- Combinación de ambos (wait + polling ligero adicional).

Frase para entrevistas: "En CI, `sleep` fijo es anti-patrón. Se usa `--wait` con timeout o polling activo con reintentos, y siempre combinado con step de logs bajo `if: failure()` y cleanup bajo `if: always()`".

### Redundancia aparente en CI = separación de responsabilidad

Cuando dos jobs de CI parecen hacer trabajo similar (job 1 compila con Maven, job 2 el Dockerfile también compila internamente), no es ineficiencia. Cada job valida una dimensión distinta:

- Job Maven puro: "el código Java compila y los tests pasan".
- Job Docker build: "el Dockerfile sigue construyendo correctamente".

Un cambio en el `pom.xml` puede romper el primero sin tocar el segundo. Un cambio en el Dockerfile puede romper el segundo sin tocar el primero. Diagnóstico limpio.

### Version pinning en Actions

Siempre `@vN` mayor (ej. `@v5`) por defecto:
- `@vN.M.P` (patch fijo) solo si un patch concreto rompió algo.
- `@main` o `@latest` nunca (cambia sin previo aviso, rompe reproducibilidad).

Analogía Maven: `@v5` es como `<version>5.+</version>` — pero en Actions es aceptable porque las actions oficiales son estables dentro de major.

### Trigger `pull_request` en Actions valida la fusión hipotética

Cuando abres PR desde `feature/x` contra `main`, GitHub ejecuta el workflow contra un **merge commit virtual** que calcula al vuelo, no contra `main` ni contra `feature/x` tal cual. Por eso detecta conflictos semánticos post-merge que Git no marca.

Combinar `push: main` (feedback confirmatorio, o para pushes directos) + `pull_request: main` (feedback preventivo, valida el merge antes de que ocurra).
