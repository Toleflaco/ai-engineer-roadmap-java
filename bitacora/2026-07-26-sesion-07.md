# Sesión 07 — Manejo de errores homogéneo con RFC 7807 en document-analyzer-ai

- **Fecha:** 2026-07-26
- **Fase:** 1 (Fundamentos LLM + Spring AI core)
- **Duración:** ~50 min (media-mañana, aprox 7:45–8:35)
- **Estado del roadmap:** Fase 1 en curso. Manejo de errores homogéneo RFC 7807 en `document-analyzer-ai`.

## Contexto

Sesión posterior a la Sesión 06 del mismo día. En la Sesión 06 quedaron dos deudas operativas observadas empíricamente: `MultipartException` respondiendo HTTP 500 en `/analyze/pdf` cuando falta el fichero, y `BeanOutputConverter` propagando excepción como HTTP 500 cuando el modelo devuelve JSON malformado. Esta sesión sanea ambas mediante un handler global con formato RFC 7807. Se decidió tomar solo el primero de los tres bloques planificados como "algo más" al final de la Sesión 06; los otros dos (extender schema `CvSummary` e introducir logging estructurado LLM) quedan explícitamente para el siguiente día de estudio, antes del salto a Fase 2.

## Qué se hizo

Se hizo un bloque conceptual corto sobre `@RestControllerAdvice` y `@ExceptionHandler`, apoyándose en el conocimiento previo de `ProblemDetail` RFC 7807 ya aplicado en `task-manager-api`. El default de Spring Boot ante excepciones no manejadas es HTTP 500 con stack trace en el body, semánticamente incorrecto para errores de cliente y con exposición de estructura interna.

Se decidió un handler global del proyecto (`GlobalExceptionHandler` en package nuevo `exception/`) en lugar de un handler específico por package: `document-analyzer-ai` es un proyecto pequeño de un solo dominio, y la separación por package aporta ceremonia sin valor; se puede refactorizar cuando el proyecto crezca.

Se creó `src/main/java/dev/toleflaco/document_analyzer_ai/exception/GlobalExceptionHandler.java` con anotación `@RestControllerAdvice` y un primer método handler para `MultipartException`, que traduce a HTTP 400 Bad Request mediante `ProblemDetail.forStatusAndDetail(...)`, con título "Petición multipart inválida" y detail prescriptivo indicando al cliente el formato esperado. No se usó el mensaje original de la excepción, considerado demasiado técnico para el cliente.

Se verificó empíricamente el primer handler: `POST /analyze/pdf` sin fichero devuelve HTTP 400 con `Content-Type: application/problem+json`, con el campo `instance` inyectado automáticamente por Spring con el valor `/analyze/pdf`, sin código explícito. Se verificó que el camino feliz de `POST /analyze/pdf` con PDF real seguía intacto.

Antes de escribir el segundo handler se hizo un diagnóstico empírico: se creó un endpoint temporal `GET /debug/converter-failure` en `AnalyzePdfController` que llama a `converter.convert("esto no es json valido para CvSummary")` para provocar el fallo del `BeanOutputConverter` y observar el tipo exacto de excepción propagada, en lugar de adivinar el nombre de la excepción.

El diagnóstico arrojó que la excepción es `tools.jackson.core.exc.StreamReadException`, que hereda de `tools.jackson.core.JacksonException`, que hereda de `RuntimeException`. Se observó que el package es `tools.jackson.core`, no `com.fasterxml.jackson.core`: es Jackson 3.x, la reescritura reciente que Spring AI 2.0 usa por debajo.

Se decidió capturar `JacksonException` en el handler en lugar de `StreamReadException`, para cubrir toda la familia (errores de tokenización y errores de mapeo semántico) con un único handler; si el modelo devuelve JSON válido pero con campos mal tipados, la excepción sigue heredando de `JacksonException`.

Se amplió `GlobalExceptionHandler` con el segundo método handler para `JacksonException`, que traduce a HTTP 502 Bad Gateway: el backend actúa como gateway ante Claude, y una respuesta inválida del upstream es semánticamente 502, no 400 (no es fallo del cliente) ni 500 (no es fallo del backend). El `ProblemDetail` lleva título "Respuesta de LLM no procesable" y detail operativo indicando al cliente reintentar.

Se verificó empíricamente el resultado final con cuatro pruebas: `GET /debug/converter-failure` devuelve HTTP 502 con problem detail de LLM; `POST /analyze/pdf` sin fichero sigue devolviendo HTTP 400 (regresión del primer handler); `POST /analyze/pdf` con PDF real sigue devolviendo `CvSummary` normal; `POST /analyze` con texto plano sigue devolviendo `CvSummary` normal.

Se borró el endpoint temporal `debugConverterFailure` de `AnalyzePdfController` una vez cumplida su función diagnóstica. Se verificó empíricamente que `GET /debug/converter-failure` devuelve HTTP 404 tras el borrado.

Durante el borrado del endpoint temporal se detectó una línea en blanco residual al final del método restante en `AnalyzePdfController.java`, mediante `git diff` antes del commit, y se descartó con `git restore`: mismo patrón de disciplina de diff aplicado en la Sesión 06.

Se hizo un commit atómico bilingüe (`2a2cab6`, inglés primero) con un único artefacto nuevo (`GlobalExceptionHandler.java`), empujado a `origin/main`.

Tras verificar el 404 del endpoint borrado se apuntó una nota observacional: la respuesta 404 vuelve a llevar stack trace en el body, porque no existe handler para `NoResourceFoundException` de Spring Web. Es el mismo tipo de deuda de higiene que se acaba de saldar para los otros dos casos; no cubierto en esta sesión.

## Decisiones y aprendizajes

Se decidió un handler global único frente a un handler por package, justificado en el tamaño actual del proyecto, con refactor previsto cuando crezca.

Se decidió diagnosticar empíricamente la excepción exacta antes de escribir el handler, en lugar de adivinar clases de Jackson: refuerzo del patrón "primero datos, después diagnóstico" ya asentado en sesiones previas.

Se hizo un descubrimiento silencioso: Spring AI 2.0 usa Jackson 3.x (`tools.jackson.core`) por debajo, no Jackson 2.x (`com.fasterxml.jackson.core`). Detalle sin impacto operativo hoy pero apuntado para no confundir imports en el futuro.

Se decidió capturar `JacksonException` (raíz de la familia) en lugar de `StreamReadException` (hoja específica), cubriendo tokenización y mapeo con un único handler. El trade-off es menos granularidad para métricas en un futuro sistema de observabilidad.

Se decidió el status HTTP 502 Bad Gateway para el fallo del LLM, justificado por RFC 7231: el backend es gateway hacia Claude, y una respuesta inválida del upstream es 502. Se descartaron como alternativas 400 (no es fallo del cliente) y 500 (no es fallo del backend).

Se decidió un mensaje operativo ("se recomienda reintentar") frente a un mensaje descriptivo del error interno: el cliente sabe qué acción tomar sin conocer detalles de Jackson.

Se reforzó el aprendizaje operativo de verificar `git diff` antes de commit para detectar líneas en blanco residuales que no aportan valor, aplicado por segunda vez en el mismo día, tras aparecer en la Sesión 06 al mover el método `analyzePdf` al fichero correcto.

Se apuntó explícitamente en el commit una deuda: el handler no loggea la excepción original. En producción esto ocultaría patrones de fallo (deriva de prompt, degradación de upstream, cambios de API). Se introducirá junto con el logging estructurado de LLM en la siguiente sesión.
