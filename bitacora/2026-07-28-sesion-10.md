## Marco conceptual: MCP y function calling

La primera hora larga de la sesión fue conceptual, antes de tocar código. Puntos que quedaron cerrados:

Function calling es el mecanismo base: el LLM emite peticiones de tools en formato estructurado, el código del cliente las ejecuta, y el LLM sigue razonando con el resultado. El LLM nunca ejecuta, solo pide.

ReAct es function calling en bucle dentro de un mismo turno de usuario, hasta que el modelo decide que tiene suficiente para responder. Conecta con el guardrail de presupuesto máximo de operaciones acordado en la Sesión 09.

MCP (Model Context Protocol) es una capa estándar por encima de function calling. Sustituye la integración cuadrática M clientes × N servicios por una relación M + N. El LLM no sabe que MCP existe; sigue haciendo function calling. Lo que cambia es de dónde vienen las tools y quién las ejecuta.

Se estableció la distinción entre agente y cliente MCP como categorías ortogonales: `erp-purchasing-agent` será ambas cosas, pero son conceptos independientes entre sí.

Sobre transportes MCP, se comparó stdio (procesos locales) con HTTP (servicios en red), y se eligió HTTP porque `erp-mcp-server` es una aplicación Spring Boot desplegable.

## Trabajo técnico: esqueleto de erp-mcp-server

Repo creado en GitHub (`Toleflaco/erp-mcp-server`) con README, `.gitignore` de plantilla Java y licencia MIT, por consistencia con `document-analyzer-ai`. Clonado a `~/proyectos/erp-mcp-server`.

Esqueleto generado con Spring Initializr: Spring Boot 4.1.0, Java 21, Maven, `groupId dev.toleflaco`, `artifactId erp-mcp-server`. Dependencias iniciales: webmvc, data-jpa, validation, h2console. Se dejó fuera deliberadamente el starter de Spring AI MCP Server, que se añadirá a mano en una sesión posterior.

El zip de Initializr se integró en el repo ya clonado: descompresión a `/tmp` y copia selectiva, fusionando el `.gitignore` de GitHub con el de Initializr para conservar cobertura completa. Se descartó `HELP.md`.

Al inspeccionar el `pom.xml` aparecieron artifactIds no reconocidos: `spring-boot-starter-webmvc`, `spring-boot-h2console`, `spring-boot-starter-*-test`. Una búsqueda web confirmó que Spring Boot 4.0 introdujo modularización profunda de las auto-configuraciones: `spring-boot-starter-web` pasó a llamarse `spring-boot-starter-webmvc`, la consola H2 se extrajo a `spring-boot-h2console`, y cada starter principal tiene ahora su contrapartida `-test`. Aprendizaje anotado: al arrancar un proyecto nuevo con Spring Boot 4, verificar los starters contra la migration guide antes de darlos por buenos.

Se ajustó el `pom.xml`: se rellenaron `<name>` y `<description>`, y se eliminaron los bloques self-closing vacíos (`<licenses>`, `<developers>`, `<scm>`, `<url>`).

Se creó estructura package-by-feature bajo `dev.toleflaco.erpmcpserver`: paquetes `product`, `supplier`, `purchaseorder`, `invoice`.

Se implementaron y verificaron empíricamente tres entidades JPA:

- `Supplier`: entidad independiente. Campos `id`, `name`, `contactEmail`. Único setter: `contactEmail`.
- `Product`: `@ManyToOne` unidireccional a `Supplier` (LAZY, FK no nula). Campos `id`, `name`, `category`, `unitPrice` (`BigDecimal`), `stock`, `minStock`. Setters solo en los tres campos con lógica de mutación real: `unitPrice`, `stock`, `minStock`.
- `PurchaseOrder`: `@ManyToOne` a `Supplier`. `status` como enum `PurchaseOrderStatus` (`DRAFT`/`SENT`/`RECEIVED`/`CANCELLED`) persistido como `STRING`. `createdAt` como `OffsetDateTime` inmutable, asignado por `@PrePersist` en UTC. Único setter: `status`. Sin `@OneToMany` a líneas todavía; se añadirá cuando exista `PurchaseOrderLine`.

Ninguna de las tres lleva `equals`/`hashCode` ni `toString`, por minimalismo: se añaden si aparece una necesidad real. La tabla de `PurchaseOrder` se nombró `purchase_orders` en snake_case, para anticipar el problema de `ORDER` como palabra reservada al migrar a PostgreSQL en la Sesión 15.

Se configuró `application.properties`: datasource H2 en memoria (`jdbc:h2:mem:erpdb`), `ddl-auto=create-drop`, logging de SQL con formato, consola H2 en `/h2-console`.

Verificación empírica final: `./mvnw spring-boot:run` arranca limpio, Hibernate genera las tres tablas (`suppliers`, `products`, `purchase_orders`), y la consola H2 es accesible desde el navegador, con conexión y un `SELECT` sobre `suppliers` funcionando.

## Decisiones locked en Sesión 10

- H2 embebida en las Sesiones 10–14; migración a PostgreSQL en la Sesión 15, junto con Dockerfile y docker-compose.
- Mono-módulo Maven, no reactor multi-módulo. Package-by-feature dentro del módulo.
- Relaciones JPA unidireccionales por defecto. Se justifica hacerlas bidireccionales solo si aparece un caso concreto que no se resuelva mejor con una query en el repositorio.
- Enums persistidos siempre como `STRING`, nunca `ORDINAL`.
- `FetchType.LAZY` explícito en todas las `@ManyToOne`.
- Minimalismo en entidades: sin auditoría, sin soft delete, sin `@Version`, sin `equals`/`hashCode`, sin `toString`. Se añaden si el uso real lo justifica.
- Snake_case en nombres de tabla, para anticipar la migración a PostgreSQL.
