## Objetivo de la sesión

Verificar ambas end-to-end con mcp-inspector antes de dar el bloque por cerrado.

## Trabajo técnico

### Tool 1: `listLowStockProducts()`

Ubicada en `ProductQueryTools`, dominio Product. Sin parámetros, retorna `List<ProductInfo>`.

Criterio de negocio: `stock <= minStock` (reorder point), no `stock < minStock`. Decidido explícitamente porque en ERPs reales `minStock` modela el punto de reorden; alcanzarlo ya es la señal para reponer. Consistente con las categorías del seed (ningún producto tiene `stock == minStock` exacto, así que el criterio A vs B no cambia el resultado observable, pero sí el significado semántico).

Query en `ProductRepository` mediante `@Query` JPQL, no derived query. Motivo: derived queries no expresan comparación entre dos columnas de la misma fila. JPQL sí:

```java
@Query("SELECT p FROM Product p WHERE p.stock <= p.minStock")
List<Product> findLowStockProducts();
```

Se extrajo un helper privado `toDto(Product)` en `ProductQueryTools` para centralizar el mapping `Product → ProductInfo` y eliminar duplicación. `getProduct` se refactorizó para consumirlo:

```java
productRepository.findById(id).map(this::toDto).orElse(null);
```

Decisión sobre `toDto`: método privado de instancia en el `@Service`, no static, no en el record `ProductInfo`, no clase `ProductMapper` aparte. Argumento: minimalismo consistente con el resto del proyecto y flexibilidad ante roce futuro (por si mañana depende de estado inyectado).

`@Transactional(readOnly = true)` obligatorio por acceso lazy a `product.getSupplier().getName()` en el mapping, con `open-in-view=false`.

Description del `@Tool` en inglés, plural, comunicando caso de uso:

> "List all products that have reached or fallen below their minimum stock threshold. Use this to identify which products need to be reordered. Returns product name, category, unit price, current stock, minimum stock threshold, and supplier name."

### Tool 2: `findProductsByCategory(String category)`

Ubicada en `ProductQueryTools`, dominio Product. Recibe `String category`, retorna `List<ProductInfo>`.

Derived query `findByCategory(String)` en `ProductRepository`, sin `@Query`. Contraste pedagógico deliberado con `findLowStockProducts`: campo contra parámetro → derived; campo contra campo → JPQL.

Decisión sobre tipo del parámetro: `String` en tool y repositorio (opción A), no enum. Coherente con el estado actual de `Product.category` como `String` en la entidad (la memoria heredada sugería enum, pero verificación empírica en el fichero mostró `String`). Si en Sesión 15 se sube a enum, refactor localizado.

Uso de `@ToolParam(description = ...)` sobre el parámetro `category` para enumerar valores válidos:

```java
@ToolParam(description = "Category name in uppercase (e.g., COFFEE, DAIRY, TEA, SWEETENERS, EQUIPMENT, PACKAGING).")
String category
```

Anotación de Spring AI aplicada al parámetro, no al método. Genera propiedad `description` en el JSON schema del parámetro, distinta del `description` de la tool. Guía al LLM sobre valores válidos sin adivinanza. Import: `org.springframework.ai.tool.annotation.ToolParam`.

Naming de la tool: `findProductsByCategory`, prefijo `find` para búsqueda con criterio. Convención establecida en esta sesión: `get*` para uno por identidad, `list*` para enumeración amplia, `find*By*` para búsqueda con criterio. Tres roles distintos para que el catálogo sea legible por el LLM sin leer descriptions.

## Verificación end-to-end con mcp-inspector

Con mcp-inspector v2, Streamable HTTP contra `http://localhost:8080/mcp`.

**`listLowStockProducts()`:**

- Devuelve 7 productos (verificado contra seed).
- SQL generado: 1 SELECT de `products` con `WHERE p.stock <= p.min_stock`, sin JOIN, más 6 SELECTs individuales a `suppliers`.
- Predicción antes de invocar: 1 + N suppliers únicos (no 1 + N productos), aplicando persistence context de primer nivel de Hibernate. Contraste explícito con la fórmula ingenua "N+1 = 1 + N productos". En este caso: 7 productos con 6 suppliers únicos (los ids 2 y 3 comparten "Andes Green Coffee Import") → 1 + 6 = 7 SELECTs. Predicción cumplida.
- Todos los `supplierName` poblados en la respuesta JSON.

**`findProductsByCategory("COFFEE")`:**

- Devuelve 6 productos (verificado contra seed).
- SQL generado: 1 SELECT de `products` con `WHERE p1_0.category = ?`, más 2 SELECTs a `suppliers`.
- Predicción antes de invocar: 6 productos, 2 suppliers únicos (Andes Green Coffee Import y Tostadores del Norte, 3 productos cada uno), esperados 1 + 2 = 3 SELECTs. Predicción cumplida al 100% (esta vez determinista desde el `data.sql`, no dependiente de casualidad).

## Errores útiles cometidos

- Description de `listLowStockProducts` inicialmente en singular ("Get detailed information about a product with stock..."), casi copia-pega de `getProduct`. Corregido tras señalar el problema: los descriptions son la única señal que tiene el LLM para distinguir tools; singular frente a plural es información semántica relevante para el modelo. Regla: describir qué hace y para qué se usa, verbo en plural si devuelve lista.
- Asunción implícita de que `Product.category` era enum, basada en memoria heredada del proyecto ("enums como STRING"). Verificación en el código real mostró que es `String` puro. Regla derivada: cuando la memoria heredada afirme algo sobre el código y el código esté delante, verificar antes de aceptar.
- Bug de compilación en `@ToolParam`: paréntesis de cierre perdido antes de `String category`. Patrón recurrente ya documentado: autocomplete o edición sin releer carácter a carácter. Detectado antes de guardar el fichero, no llegó a IDE.
- Primera versión del commit de `listLowStockProducts` describía infraestructura que ya existía desde Sesión 12 (`@Service` con `@Tool`, `ToolCallbackProvider`) y omitía lo realmente nuevo (`@Query` JPQL con columnas, helper `toDto` extraído, refactor de `getProduct`). Regla reforzada: el commit describe lo que cambia respecto al estado anterior, no las convenciones ya establecidas.

## Decisiones locked de la sesión

Se suman a las de Sesiones 10, 11, 11.5 y 12, sin sustituir ninguna:

- **Naming convention de tools MCP**: prefijo `get` para uno por identidad, `list` para enumeración amplia sin criterio, `find...By...` para búsqueda con criterio. Tres roles semánticos distintos, legibles por el LLM en el catálogo sin leer descriptions.
- **Helper de mapping en el `@Service`, no en el record ni en clase aparte**. Método privado de instancia `toDto(<Entity>)` en cada `<Domain>QueryTools`. Minimalismo consistente. Si mañana el mapping crece o se comparte, revisitable con `ProductMapper` explícito.
- **`@ToolParam(description = ...)` sobre el parámetro cuando el input admite un catálogo cerrado de valores o requiere formato específico** (case, unidades, formato de fecha). Enumeración de valores válidos en la description del ToolParam, no en la del `@Tool`, para separar responsabilidades en el JSON schema. Paquete `org.springframework.ai.tool.annotation.ToolParam`.
- **Reglas de description de `@Tool`**: (1) verbo en plural si la tool devuelve lista; (2) comunicar caso de uso además de mecánica; (3) siempre en inglés; (4) el LLM lee la description para decidir cuándo llamar la tool, no solo qué devuelve.
- **Criterio N+1 refinado**: con persistence context de primer nivel, la fórmula real es `1 + N suppliers únicos`, no `1 + N productos`. Diferencia observable en logs de Hibernate. Deuda técnica sobre N+1 se pospone hasta que el volumen o el análisis empírico lo justifique; no se introduce `JOIN FETCH` ni `@EntityGraph` en tools de lectura simples de esta sesión.
- **Regla `@Query` vs derived query**: campo contra parámetro → derived query; campo contra campo (misma fila) → `@Query` JPQL.
- **Deuda técnica menor sobre case sensitivity**: derived queries de Spring Data son case-sensitive por defecto. `findByCategory("coffee")` no encuentra `"COFFEE"`. Solución (`IgnoreCase` sufijo o normalización en el servicio) queda diferida hasta que aparezca el problema empírico.
