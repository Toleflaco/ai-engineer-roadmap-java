# Sesión 03 — IntelliJ IDEA en Linux nativo dentro de WSL

- **Fecha:** 2026-07-24
- **Fase:** 1 (Fundamentos LLM + Spring AI core)
- **Duración:** ~1h45 (franja tarde-tarde, aprox 15:15–17:00)
- **Estado del roadmap:** Fase 1 en curso. Deuda de entorno de desarrollo (IntelliJ en WSL) saldada.

## Contexto

Sesión dedicada a saldar la deuda técnica de prioridad alta identificada en la Sesión 02: IntelliJ IDEA en Linux nativo dentro de WSL, para eliminar la fricción de editar archivos de WSL desde IntelliJ Windows.

## Qué se hizo

Se instaló JetBrains Toolbox 3.6.2 en Ubuntu WSL 22.04. Se instalaron primero los prerequisitos de sistema con apt (`libfuse2` y `dbus-user-session`), se descargó el tarball desde `download.jetbrains.com` con la URL obtenida vía la API oficial de releases de JetBrains (`data.services.jetbrains.com`), y se verificó el checksum SHA256 antes de extraer. La instalación se hizo bajo el home del usuario (`~/apps/jetbrains-toolbox/`), sin sudo y sin usar `/opt`.

Desde Toolbox se instaló IntelliJ IDEA en su edición unificada (Community+Ultimate, disponible desde diciembre 2025), con login mediante cuenta JetBrains. Tras comprobar que la instalación había arrancado por defecto en modo trial, se activó explícitamente la suscripción Ultimate mediante `Help > Register > Activate Another Subscription`. La suscripción queda activa hasta el 22/08/2026, con degrade automático posterior a la capa gratuita de la edición unificada.

Se verificó el entorno completo de forma empírica: apertura del proyecto `document-analyzer-ai` desde la ruta Linux nativa `/home/tole/proyectos/document-analyzer-ai` (no vía `\\wsl$\...`), detección automática del JDK 21 (Temurin) por parte de IntelliJ, `./mvnw compile` en verde desde la terminal integrada, integración de Git operativa con SSH, y arranque de Spring Boot con respuesta correcta del endpoint `/chat`.

Se diagnosticó y corrigió un problema con el preview de Markdown, que no renderizaba pese al toggle correcto. El diagnóstico llevó a JCEF (Java Chromium Embedded Framework), el componente que IntelliJ usa para renderizar previews, que no arrancaba por dependencias de sistema faltantes. Se verificó con `ldd cef_server | grep "not found"`, que señaló como faltantes `libnspr4.so` y `libasound.so.2`. Se instalaron `libnss3` (que arrastra `libnspr4` como dependencia transitiva) y `libasound2`, y una segunda pasada de `ldd` confirmó que ya no faltaban librerías. El preview de Markdown quedó funcional tras reiniciar el IDE.

Se delegó a Claude Code la redacción de la bitácora de Sesión 02, con dos pasadas de revisión, una de las cuales derivó en una corrección aplicada (reformulación de la deuda técnica de IntelliJ). El commit resultante, en formato Conventional Commits bilingüe, se empujó a `origin/main` del hub.

## Decisiones y aprendizajes

Se decidió instalar Toolbox bajo el home del usuario (`~/apps/`) sin sudo, en lugar de en `/opt/` a nivel de sistema. El motivo es la coherencia con el resto del stack de usuario (IDEs, cachés, configuración) que Toolbox va a gestionar bajo home de todas formas.

Se verificó empíricamente el checksum SHA256 del tarball descargado antes de ejecutarlo, como higiene de instalación de binarios descargados de internet.

Se adoptó la edición unificada de IntelliJ IDEA (una sola descarga, con features controladas por suscripción) como estrategia para no tener que reinstalar nada cuando caduque la suscripción Ultimate en agosto de 2026.

Del diagnóstico de JCEF se extrajo un aprendizaje empírico de alcance general: `ldd | grep "not found"` es la herramienta canónica para diagnosticar shared libraries faltantes en Linux, aplicable a cualquier binario, no solo a IntelliJ.

Se completó la primera delegación real de una bitácora completa a Claude Code (la de Sesión 02), con un bucle de revisión de dos pasadas: propuesta, filtro sobre adjetivos y voz, corrección específica, aprobación.

Se identificó un aprendizaje metodológico transversal. Durante el diagnóstico del preview de Markdown, la conversación con Claude descartó inicialmente el problema como un toggle de UI mal pulsado, sin pedir verificación empírica antes de asumirlo. El problema resultó ser real, a nivel de sistema (dependencias de JCEF faltantes). Se adoptó como corrección: primero datos, después diagnóstico, tanto en la interacción con Claude como en el uso de Claude Code.
