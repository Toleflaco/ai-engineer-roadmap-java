# Sesión 12 — Starter Spring AI MCP Server y primera tool en erp-mcp-server

- **Fecha:** 2026-07-29
- **Fase:** 2 (Tool calling, agentes y MCP)
- **Duración:** ~2h, sesión de mañana
- **Estado del roadmap:** Sesión 12 completada. `erp-mcp-server` expone su primera tool (`getProduct`) verificada end-to-end contra un cliente MCP real.

## Contexto

Tras la Sesión 11.5 (seed data en H2), esta sesión aborda el corazón de la Fase 2: montar el starter de Spring AI MCP Server y exponer la primera tool de lectura, verificándola contra un cliente MCP real en lugar de dar por buena la integración solo porque el servidor arranca.

## Objetivo de la sesión

Dos bloques: (1) añadir el starter MCP y la configuración base del servidor, verificando que la autoconfiguración carga correctamente; (2) escribir la primera tool, `getProduct(id)`, y verificarla con `mcp-inspector` haciendo el handshake `initialize` y una invocación real de la tool.

## Trabajo técnico

### Bloque 1: starter MCP + configuración base

En `pom.xml` se añadió un bloque `<dependencyManagement>` importando el BOM de Spring AI:

```xml
<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>org.springframework.ai</groupId>
            <artifactId>spring-ai-bom</artifactId>
            <version>2.0.0</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>
```

Y la dependencia del starter, sin versión explícita (resuelta por el BOM):

```xml
<dependency>
    <groupId>org.springframework.ai</groupId>
    <artifactId>spring-ai-starter-mcp-server-webmvc</artifactId>
</dependency>
```

Se eligió el starter `-webmvc` (no `-webflux`) por coherencia con el resto del stack, que es JPA blocking sobre Spring MVC.

En `application.properties` se registró la identidad declarativa del servidor:

```properties
spring.ai.mcp.server.name=erp-mcp-server
spring.ai.mcp.server.version=0.0.1
```

Transporte, path y protocolo se dejaron en sus valores por defecto en este primer paso — el ajuste de protocolo llegaría en el bloque 2, forzado por la verificación con el Inspector.

**Verificación intermedia — dependency tree.** `./mvnw dependency:tree | grep -iE "spring-ai|mcp"` confirmó que el BOM resolvió el starter a la versión `2.0.0` y trajo transitivamente:

- `io.modelcontextprotocol.sdk:mcp:2.0.0` — SDK oficial de MCP.
- `spring-ai-autoconfigure-mcp-server-webmvc` — autoconfiguración Spring Boot del server.
- `mcp-spring-webmvc` — transporte sobre Spring MVC.
- `spring-ai-mcp-annotations` — anotaciones MCP (`@McpTool` y afines, no usadas en esta sesión).

**Verificación de arranque.** `./mvnw spring-boot:run` arrancó limpio en ~3s. El log confirmó dos líneas relevantes:

```
McpServerAutoConfiguration : Enable tools capabilities, notification: true
SyncMcpToolProvider        : No tool methods found in the provided tool objects: []
```

La segunda línea era el resultado esperado: la autoconfiguración carga correctamente, pero todavía no hay ninguna tool registrada, porque ese es justo el trabajo del bloque 2.

### Bloque 2: primera tool MCP, `getProduct`

**`ProductRepository`** — interfaz mínima:

```java
public interface ProductRepository extends JpaRepository<Product, Long> {
}
```

Sin métodos custom: `findById` heredado de `JpaRepository` basta para esta tool.

**`ProductInfo`** — record DTO de transporte, con 7 campos:

```java
public record ProductInfo(
        Long id,
        String name,
        String category,
        BigDecimal unitPrice,
        Integer stock,
        Integer minStock,
        String supplierName
) {
}
```

El punto de diseño discutido fue `supplierName`: aplanado como `String` en lugar de anidar un `SupplierInfo` con su propio record. Motivo doble — reduce ruido en el JSON Schema que el LLM ve al decidir si invocar la tool, y evita que la tool arrastre serialización de un grafo de entidades más allá de lo que el caso de uso necesita.

**`ProductQueryTools`** — `@Service` con la tool:

```java
@Service
public class ProductQueryTools {

    private final ProductRepository productRepository;

    public ProductQueryTools(ProductRepository productRepository) {
        this.productRepository = productRepository;
    }

    @Transactional(readOnly = true)
    @Tool(description = "Get detailed information about a product by its ID. " +
            "Returns product name, category, unit price, current stock, " +
            "minimum stock threshold, and supplier name.")
    public ProductInfo getProduct(Long id) {

        return productRepository.findById(id)
                .map(product -> new ProductInfo(
                        product.getId(),
                        product.getName(),
                        product.getCategory(),
                        product.getUnitPrice(),
                        product.getStock(),
                        product.getMinStock(),
                        product.getSupplier().getName()
                ))
                .orElse(null);
    }
}
```

Dos puntos técnicos relevantes:

- `@Transactional(readOnly = true)` es necesario porque `product.getSupplier().getName()` accede a una relación `@ManyToOne` LAZY. Con `open-in-view=false` (decisión locked de Sesión 11), no hay sesión Hibernate abierta fuera del método de servicio; sin la transacción, esa llamada lanzaría `LazyInitializationException`.
- El import de `@Transactional` debe ser `org.springframework.transaction.annotation.Transactional`, no `jakarta.transaction.Transactional`. La anotación de Jakarta no tiene atributo `readOnly()` — error real cometido en esta sesión, ver más abajo.

**Registro de la tool.** En `ErpMcpServerApplication` se añadió un único bean:

```java
@Bean
ToolCallbackProvider erpTools(ProductQueryTools productQueryTools) {
    return MethodToolCallbackProvider.builder()
            .toolObjects(productQueryTools)
            .build();
}
```

Convención adoptada: un único `ToolCallbackProvider` para todo el servidor, que irá agregando servicios de distintos dominios vía varargs en `.toolObjects(...)` a medida que crezcan las tools, en lugar de un bean por servicio.

**Ajuste de protocolo.** Se añadió a `application.properties`:

```properties
spring.ai.mcp.server.protocol=STREAMABLE
```

Este cambio no estaba planeado al empezar el bloque; salió de la verificación con el Inspector (ver siguiente sección). El default de Spring AI 2.0 para `protocol` es `SSE`, transporte marcado deprecated que expone endpoints en `/sse` y `/mcp/message`. `mcp-inspector v2` conecta por Streamable HTTP contra un único endpoint `/mcp`, y sin este ajuste la conexión fallaba con 404.

### Verificación end-to-end con mcp-inspector v2

Instalación vía `npx @modelcontextprotocol/inspector`, versión 2 (no v1). UI en `http://localhost:6274` con session token en query string, backend proxy corriendo en `:6277`. Diferencia de modelo mental respecto a v1: el Inspector v2 mantiene un catálogo de servers, cada uno como tarjeta conectable de forma independiente, en lugar de una única conexión activa.

Configuración de la tarjeta de conexión:

- **Name:** `erp-mcp-server`
- **Transport type:** `Streamable HTTP`
- **URL:** `http://localhost:8080/mcp`

**Primer intento: FAILED, 404.** Este fallo fue el disparador que reveló que el protocolo por defecto del servidor era `SSE`, no Streamable HTTP — un dato que no se había verificado antes de intentar conectar, sino a través del propio fallo de conexión. Fix: añadir `spring.ai.mcp.server.protocol=STREAMABLE`.

**Segundo intento: CONNECTED.** El log del servidor registró el handshake:

```
Client initialize request - Protocol: 2025-11-25,
Capabilities: ClientCapabilities[...],
Info: Implementation[name=mcp-inspector, ...]
```

El panel "Connection Info" del Inspector confirmó:

- **Server Implementation:** name `erp-mcp-server`, version `0.0.1`, protocol `2025-11-25`, transport `STREAMABLE-HTTP`, session-based.
- **Server Capabilities activas:** Tools, Resources, Prompts, Logging, Completions.
- **Extensions cliente advertidas:** `io.modelcontextprotocol/tasks`, `io.modelcontextprotocol/ui`.

**Invocación manual** desde la pestaña Tools, `getProduct(id=1)`, devolvió:

```json
{
  "id": 1,
  "name": "Café verde Colombia Supremo",
  "category": "COFFEE",
  "unitPrice": 12.5,
  "stock": 40,
  "minStock": 20,
  "supplierName": "Andes Green Coffee Import"
}
```

Cadena completa verificada de punta a punta: transport HTTP MCP → autoconfiguración del starter → resolución de la tool por nombre → invocación del método `@Service` → apertura de transacción read-only → `productRepository.findById` → lazy load de `Supplier` dentro de la transacción → construcción del record → serialización JSON → respuesta al cliente. El dato coincide exactamente con la fila `id=1` sembrada en la Sesión 11.5 (`Café verde Colombia Supremo`, proveedor `Andes Green Coffee Import`).

## Errores útiles cometidos

- **Import equivocado de `@Transactional`.** Primera versión de `ProductQueryTools` importaba `jakarta.transaction.Transactional`. El IDE marcó `cannot find @interface method 'readOnly()'` porque esa anotación no tiene ese atributo. Fix: cambiar el import a `org.springframework.transaction.annotation.Transactional`.
- **Escape sequence rota (`\ `) en la descripción del `@Tool`**, arrastrada de un salto de línea mal editado al concatenar los tres fragmentos del `description`. Fix: eliminar la barra invertida sobrante.
- **Asunción incorrecta sobre el protocolo por defecto.** Se asumió, sin comprobarlo, que el default de `spring.ai.mcp.server.protocol` sería compatible con Streamable HTTP. En realidad el default es `SSE`, deprecated en Spring AI 2.0. El error salió a la luz por el 404 del Inspector, no por lectura previa de la documentación — lo que confirma la utilidad de dejar el commit de la tool para después de la verificación con un cliente real, no antes.

## Decisiones locked de la sesión

Se suman a las de Sesiones 10, 11 y 11.5, sin sustituir ninguna:

- **Ruta de tools MCP: opción A** (`@Tool` de Spring AI + `MethodToolCallbackProvider`), no opción B (`@McpTool`, también disponible vía `spring-ai-mcp-annotations`). Es la ruta principal de la documentación oficial de Spring AI 2.0, mayoritaria en ejemplos, y `@Tool` es transversal: la misma anotación sirve para exponer una tool a MCP y para inyectarla en un `ChatClient` local del futuro agente (`erp-purchasing-agent`).
- **Un único `@Bean ToolCallbackProvider`** para todo el servidor, agregando servicios de distintos dominios vía varargs en `.toolObjects(...)` a medida que crezcan.
- **Descripciones de tools siempre en inglés**, incluso con dominio de negocio en español. Convención estándar del ecosistema de tool calling con LLMs.
- **DTOs de respuesta a MCP: records aplanados.** Ni entidades JPA directamente (expondrían el grafo y podrían disparar N+1 fuera de la transacción), ni `Map<String, Object>` (Spring AI no puede generar un JSON Schema tipado a partir de un mapa). Las relaciones a un nivel se aplanan a `String` (`supplierName`), sin anidar otros records salvo que aparezca una justificación concreta.
- **Naming convention: `<Domain>QueryTools` para lectura, `<Domain>WriteTools` (o equivalente) para escritura futura.** Separación CQRS ligera desde el arranque de la superficie de tools.
- **`@Transactional(readOnly = true)` obligatorio** en cualquier tool que acceda a relaciones LAZY, mientras el proyecto mantenga `open-in-view=false`.
- **Import de `@Transactional` siempre desde `org.springframework.transaction.annotation.Transactional`.** Nunca desde `jakarta.transaction`, cuya anotación no soporta `readOnly`.
- **`spring.ai.mcp.server.protocol=STREAMABLE` obligatorio y explícito** en `application.properties`. El default `SSE` está deprecated en Spring AI 2.0 y no encaja con clientes modernos (Inspector v2, versiones recientes de Claude Desktop, el futuro agente).
- **Devolver `null` en "no encontrado"** en esta primera hornada de tools de lectura. Decisión marcada como revisitable en la Sesión 14, cuando entre validación explícita.
- **Verificación empírica end-to-end antes de commitear**, en cualquier bloque de trabajo que integre un cliente de protocolo externo. Regla nacida en esta sesión: si en el pipeline hay un cliente externo (Inspector, y más adelante el agente), no se da el bloque por cerrado hasta que ese cliente confirme handshake y ejecución exitosa de al menos una invocación real.
