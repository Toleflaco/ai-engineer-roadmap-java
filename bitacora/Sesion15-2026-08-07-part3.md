## Bloque S15-part-3: integración del servicio `app`

### Predicciones antes de teclear (método Sócratico)

1. **Hostname dentro de la red de compose para llegar a Postgres desde `app`.** Respuesta correcta: `postgres` (nombre del servicio).
2. **Los cuatro bloques que necesita el servicio `app`**. Respuesta parcial, matices añadidos:
   - "Del jar de la app" → **incorrecto en detalle**: no es el JAR directo, es `build: .` que apunta al Dockerfile, que a su vez copia el JAR. El Dockerfile define **imagen**; compose la construye vía `build`.
   - "URL, username/password" → correcto (declararlas todas por higiene twelve-factor, aunque solo la URL es imprescindible).
   - "on depends de postgres" → correcto pero incompleto. `depends_on` en forma corta solo espera al **arranque** del contenedor, no a que Postgres acepte conexiones. Necesario `condition: service_healthy` para esperar al healthcheck (el `pg_isready` definido en part-1).
   - "No sé si publicar 8080" → decisión asistida: **publicar** para permitir `curl` y `mcp-inspector` desde el host. Regla mental: publicar en dev por comodidad, no publicar en prod salvo necesidad.

### Concepto lockeado: DNS interno de compose

Dentro de la red de compose, el DNS resuelve por **nombre del servicio** (la clave del YAML), no por `container_name`. El `container_name: erp-postgres` solo aparece en `docker ps`; para hablar de contenedor a contenedor se usa `postgres`. Matiz importante que a veces confunde.

Corolario: `container_name` es cosmético (identificar el contenedor en `docker ps`, `docker logs erp-app`, etc.). Se puede omitir sin efecto funcional; compose autogenera nombres tipo `erp-mcp-server-app-1`.

### Concepto lockeado: env var override + twelve-factor

Problema: `spring.datasource.url=jdbc:postgresql://localhost:5432/erp` en `application.properties` funciona cuando la app arranca desde IntelliJ (host resuelve `localhost:5432` → puerto publicado por el contenedor Postgres). Pero dentro del contenedor `app`, `localhost` apunta al propio contenedor `app`, no a Postgres. Rompe.

Solución: `SPRING_DATASOURCE_URL` como env var en el servicio `app` del compose, apuntando a `jdbc:postgresql://postgres:5432/erp`. Spring Boot da precedencia a env vars sobre `application.properties`, con relaxed binding (`spring.datasource.url` ↔ `SPRING_DATASOURCE_URL`). El `.properties` sigue valiendo para IntelliJ (dev local), la env var overridea en runtime dentro del compose.

Verificación empírica al arrancar: el log de `app` mostró `Database: jdbc:postgresql://postgres:5432/erp` aunque el properties dijera `localhost` — evidencia del override funcionando.

### Bug de sintaxis YAML detectado antes de arrancar

Primer intento de `depends_on` en forma larga:

```yaml
depends_on: postgres:
  condition: service_healthy
```

YAML no parsea eso. La forma larga es un mapping donde la clave es el nombre del servicio y el valor otro mapping con `condition`. Correcto:

```yaml
depends_on:
  postgres:
    condition: service_healthy
```

Tres niveles de indentación. Confusión típica al mezclar forma corta (aceptaría `depends_on: [postgres]` o `depends_on: postgres` en línea) con forma larga (obliga a mapping multi-línea).

### YAML final del servicio `app`

```yaml
  app:
    container_name: erp-app
    build: .
    depends_on:
      postgres:
        condition: service_healthy
    environment:
      SPRING_DATASOURCE_URL: jdbc:postgresql://postgres:5432/erp
      SPRING_DATASOURCE_USERNAME: erp
      SPRING_DATASOURCE_PASSWORD: erp
    restart: unless-stopped
    ports:
      - "8080:8080"
```

Sin `image:` porque `build: .` implica que compose construye y etiqueta la imagen (por defecto `<nombre-proyecto>-app`).

### Confusiones conceptuales aclaradas al cierre

Momento de recap conceptual, correcciones a la explicación de Tole:

- **"Parte 1 arrancamos Postgres con Flyway en él"** → incorrecto. Flyway es librería Java, vive en la app Spring Boot, no en el contenedor de Postgres. En part-1 se preparó el contenedor Postgres y se portó el schema y seed a los ficheros `V1__init_schema.sql` y `V2__seed_dev_data.sql`. Flyway los aplica en runtime desde la app.
- **"Parte 2 el Dockerfile construye el jar"** → correcto con matiz. El Dockerfile define una **imagen**, no un contenedor. Símil: imagen es la clase, contenedor es la instancia.
- **"Parte 3 un contenedor con dos servicios"** → incorrecto. Son **dos contenedores**, uno por servicio. El "pegamento" es la red de compose (red bridge autogenerada), donde ambos se resuelven por DNS con el nombre del servicio.

Regla mental lockeada:
- **Imagen**: receta estática, la construye el Dockerfile.
- **Contenedor**: instancia corriendo de una imagen.
- **Servicio (compose)**: definición de cómo debe correr un contenedor: qué imagen, qué red, qué volúmenes, qué depends_on.
- **Compose**: orquestador que lee el YAML, crea la red y arranca los contenedores respetando dependencias.

Diferencia esperable en entrevistas de Docker.

## Deudas operacionales lockeadas nuevas

### YAML — forma larga de `depends_on` siempre en mapping multi-línea

La forma larga de `depends_on` (con `condition:`) exige mapping YAML multi-línea:

```yaml
depends_on:
  postgres:
    condition: service_healthy
```

Nunca `depends_on: postgres:` en la misma línea. Forma corta acepta valor escalar (`depends_on: postgres`) o lista (`depends_on: [postgres]`), pero pierde `condition`.

### Distinción service name vs container_name para DNS en compose

Dentro de la red de compose, DNS resuelve por **nombre del servicio** (clave en el YAML), no por `container_name`. `container_name` es cosmético para `docker ps`, `docker logs`, `docker exec`. Regla: usar el nombre del servicio en env vars, healthchecks y depends_on.

### `curl /mcp` con 400 y "Invalid Accept header" = verificación positiva

Cuando un endpoint MCP Streamable HTTP responde con HTTP 400 `Invalid Accept header. Expected TEXT_EVENT_STREAM`, la respuesta es **evidencia positiva** de que el endpoint existe y sirve el protocolo. El error viene de que el cliente (curl con `Accept: */*` por defecto) no habla el content-type esperado. Para verificación funcional de MCP, usar `mcp-inspector` u otro cliente que envíe `Accept: text/event-stream`.

### 404 con JSON estructurado ≠ 404 vacío

Un 404 con cuerpo JSON tipo `{"timestamp":"...","status":404,"error":"Not Found","path":"..."}` es respuesta de Spring Boot: la app está viva, Spring MVC funciona, solo falta el endpoint mapeado. Un 404 sin cuerpo o un `Connection refused` sí sería síntoma de app caída o puerto mal publicado. Diferencia útil como paso de diagnóstico.

### `docker compose up --build` como default al iterar

Al desarrollar en la app y necesitar arrancar el compose, `--build` como default:

```bash
docker compose up --build -d
```

Sin `--build`, compose reutiliza la imagen previamente construida y los cambios en código Java no se reflejan. En dev, el pequeño coste de rebuild se compensa con la garantía de que la imagen refleja el HEAD.

## Frases ⭐⭐⭐ para entrevistas

- **DNS de compose por nombre de servicio**: "dentro de la red de compose, los contenedores se resuelven por el nombre del servicio, no por container_name; container_name es solo etiqueta para docker ps".
