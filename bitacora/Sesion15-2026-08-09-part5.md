## Bloque S15-part-5: README con enfoque híbrido

### Decisiones de scope antes de redactar el prompt

Dos decisiones lockeadas antes de tocar Claude Code:

**Idioma del README: inglés**. Justificación: audiencia real es recruiter técnico y tech lead evaluando portfolio, con LinkedIn del candidato en inglés y código en inglés. Coherencia total. Un README en español limitaría audiencia al mercado ibérico sin ganar nada — los recruiters técnicos españoles leen inglés técnico sin fricción.

**Restricciones explícitas para Code**. Cuatro cosas que NO debe hacer:
- No inventar "why" detrás de decisiones (multi-stage, twelve-factor, health-gated). Eso lo añade la iteración conversacional después, con contexto de sesión.
- No añadir secciones de relleno sin sustancia (Contributing, License, Roadmap, Acknowledgements).
- No añadir badges "gimmick" (made with love, shields.io decorativos). Solo el badge del CI.
- No redactar prosa marketera (blazing fast, production-ready, cutting-edge). Tono seco, técnico.

Regla mental lockeada: **las instrucciones negativas al AI (qué NO hacer) son tan importantes como las positivas**. Sin ellas, el modelo tiende a rellenar con plantillas de portfolio genéricas.

### Diseño del prompt con contrato explícito

Estructura del prompt entregado a Code, tres bloques:

1. **What to include** — 9 secciones concretas con instrucciones de dónde leer los hechos (pom.xml para versiones, `.github/workflows/` para nombre del workflow y badge URL, clases con `@Tool` para catálogo de tools, `db/migration/` para migraciones Flyway).
2. **What NOT to include** — reformulación de las restricciones anteriores como reglas duras.
3. **Output** — instrucción de escribir en README.md (raíz), sobrescribir si existe, imprimir resumen de lo extraído al final para sanity check.

Detalle operacional relevante: se pidió a Code que **marcara como comentario cualquier traducción ES→EN que hiciera** en las descripciones de los `@Tool`. Resultó innecesario (todas las descripciones ya estaban en inglés en el código), pero era la salvaguarda correcta ante incertidumbre.

Otro detalle: instrucción explícita de **no fabricar URLs, versiones, ni file paths**. Verificar contra el repo.

### Iteración conversacional 1: sección Design decisions

Añadida a mano entre la sección Architecture (con diagrama ASCII) y MCP tools. Cinco subsecciones con nivel `###`:

1. **Self-contained multi-stage Dockerfile** — filosofía B: el Dockerfile compila el JAR internamente con `./mvnw package`, no espera JAR pre-construido. Tradeoff explícito: 2-3 min más de build, a cambio de portabilidad total (cualquiera con Docker clona y arranca sin Java/Maven/IDE).
2. **Twelve-factor configuration via environment variables** — `SPRING_DATASOURCE_URL` override desde compose. Una imagen sirve local, dev, compose, Kubernetes, prod.
3. **Health-gated startup** — `depends_on: postgres: condition: service_healthy` + `pg_isready` healthcheck. Sin esto, `app` racea a Postgres al arrancar y Flyway rompe. Distinción `depends_on` corta (solo arranque de proceso) vs. larga (espera al healthcheck) explicitada.
4. **Three-job CI pipeline with orthogonal validation** — cada job valida una dimensión (Java compila, Dockerfile construye, stack completo funciona). Redundancia aparente = separación de responsabilidad. Frase clave: "makes CI failures diagnosable without reading logs".
5. **Empirical MCP endpoint verification** — smoke test espera HTTP 400 con "Invalid Accept header. Expected TEXT_EVENT_STREAM". Evidencia POSITIVA de que el endpoint está mapeado y sirviendo el protocolo Streamable HTTP. El "error" viene del cliente (curl envía `Accept: */*`), no del servidor.

Regla mental lockeada: **cada bullet en portfolio cierra con tradeoff explícito o justificación empírica, nunca marketing**. Cuando se enumera una decisión, el lector técnico espera saber por qué y qué cuesta.

### Iteración conversacional 2: sección Known limitations

Añadida al final del README, dos entradas:

1. **No container-level healthcheck for the app service** — `Dockerfile` sin `HEALTHCHECK`, servicio `app` en compose sin healthcheck. `--wait` retorna cuando el proceso está corriendo, no cuando Spring Boot ha terminado de arrancar. Smoke test compensa con retry, pero el fix limpio es añadir `spring-boot-starter-actuator`, exponer `/actuator/health` y cablearlo tanto en el `HEALTHCHECK` del Dockerfile como en el servicio de compose.
2. **No partial receipt of purchase orders** — `receivePurchaseOrder` transiciona el pedido entero de `SENT` a `RECEIVED` en un paso. Recepciones parciales requerirían estado por línea y un status `PARTIALLY_RECEIVED` separado.

Redacción locked: **describe estado actual → describe fix o extensión**. Sin "unfortunately", sin "we know this is bad", sin apologías. Tono técnico.

Regla mental lockeada: **la honestidad técnica se lee mejor en portfolio que la omisión**. Un README con Known limitations bien articulado señala que el candidato sabe lo que dejó abierto y por qué; un README sin sección así se lee como omisión o falta de perspectiva.

## Deudas operacionales lockeadas nuevas

### Verificar en disco antes de pedir edits basados en fragmentos pegados

Cuando algo en un pegado del chat huele a artefacto (línea sospechosa, formato raro, contenido inesperado), verificar en disco con `cat`, `grep`, o abriendo el fichero en el IDE **antes** de proponer edits. Un `cat` cuesta 5 segundos y evita ediciones innecesarias sobre un contenido que no está realmente en el fichero.

Aplicable especialmente cuando el asistente inicia una revisión de un documento largo pegado en el chat.

### Instrucciones negativas al AI son parte del prompt, no opcionales

Cuando se delega redacción de artefactos con Claude Code (o cualquier LLM), el bloque "what NOT to include" es tan importante como "what to include". Sin él, el modelo rellena con plantillas genéricas que hay que borrar después.

Frase para entrevistas: "Delegar redacción a un LLM requiere contrato explícito de exclusiones. Sin restricciones negativas, el output tiende a plantillas de portfolio genéricas — badges decorativos, secciones vacías, prosa marketera. El prompt debe listar qué NO hacer con la misma precisión que qué hacer."

### README de portfolio ≠ documentación de curso

Un artefacto de portfolio (README, ADR, diagrama de arquitectura) se lee como pieza autónoma. Referencias a "Project N of Roadmap Z" o "Fase 6.5 del plan de estudios" pertenecen al diario de aprendizaje, no al artefacto público. Un tech lead evaluador no tiene contexto del roadmap del candidato — le llega el README solo.

Regla: **al generar artefactos públicos, filtrar cualquier referencia a la estructura pedagógica interna**.

### Miscalibración en cierre de subsesión con ventana larga disponible

Al terminar el commit del README el asistente propuso cerrar la subsesión, cuando la ventana estaba apenas empezada (~30 min de ~3h disponibles). Corregido por push-back directo del usuario. Aprendizaje operacional: **cuando la subsesión cierra y hay ventana claramente disponible, encadenar al siguiente hito por defecto** (aquí: diario + Redis), no ofrecer cierre como opción neutral.

## Frases ⭐⭐⭐ para entrevistas

- **Prompt engineering para delegación a AI**: "Delegar redacción de artefactos a un LLM requiere contrato explícito con instrucciones positivas (qué incluir, con lecturas verificables del código fuente) e instrucciones negativas (qué no inventar, qué secciones no rellenar, qué tono evitar). Sin el bloque de exclusiones, el output tiende a plantillas genéricas que hay que borrar después".
- **README de portfolio = artefacto autónomo**: "Un README de portfolio se lee como pieza aislada. Cualquier referencia a la estructura pedagógica interna del candidato (Project N of X, Fase Y) se filtra antes de publicar. El evaluador no tiene contexto del roadmap; le llega el README solo".
- **Honestidad técnica en portfolio**: "Una sección Known limitations bien articulada en un README se lee mejor que un README perfecto. Señala que el candidato conoce sus tradeoffs y sabe cómo cerrarlos, no que se le hayan escapado".
- **Filosofía B del Dockerfile**: "Multi-stage con build auto-contenido: el Dockerfile compila internamente el JAR con `./mvnw package`, no depende de un JAR pre-construido en el workspace. Sacrifica 2-3 minutos de build a cambio de portabilidad total. Reproducibilidad sobre velocidad".
- **Verificación empírica del MCP endpoint**: "El smoke test verifica HTTP 400 con mensaje 'Invalid Accept header. Expected TEXT_EVENT_STREAM'. Ese 400 es evidencia positiva de que el endpoint está mapeado y sirviendo el protocolo Streamable HTTP. El error viene del cliente (curl sin `Accept: text/event-stream`), no del servidor. Un 404 o 502 sería el fallo real".
- **Redundancia aparente en CI = separación de responsabilidad**: "Un pipeline con tres jobs donde build-and-test compila el código y docker-build también compila internamente no es redundante. Cada job valida una dimensión ortogonal: código Java pasa tests, Dockerfile sigue construyendo, stack completo funciona. Un fallo aislado en cualquiera de ellos apunta directamente a la dimensión rota, sin leer logs".
- **BOM-gestión de dependencias en artefactos de portfolio**: "En un README, documentar versiones resueltas por BOM del parent (Spring Boot en este caso) sería estampar un número que mentirá cuando se actualice el parent. La forma correcta es enumerar las dependencias como 'version managed by the Spring Boot parent BOM'. Refleja la práctica real y no crea documentación que envejece mal".
